## 8. Deployment — Docker / NAS / server mode  _(P6a–c)_ ✅

Done 2026-10-15: P6a (container validated, `uv.lock` build with CPU torch, non-root,
digest-pinned, healthcheck, Docker "Always keep on this device" hint), P6b (password login,
Host/Origin checks, session secret, rate limit, `127.0.0.1` default), P6c (helper M2 fixes,
start-at-login files, Settings helper card, NAS + bind-mount docs). Still untested: a real
Synology (`PUID`/`PGID`) and Docker Desktop on Windows.

- Let's rethink the docker deployment and move that to V3 as well

V1/V2 shipped Docker as-is with **native as the default**. V3 turns the container into a
proper always-on server story. The release plan is `Docker.md`; it covers Security.md **H1**
(login, bind to localhost, Host/Origin checks) and **L2** (pinned builds). The deferred
**M1** (DNS rebinding / cross-site websocket), **M2** (helper `/open`), **L1**
(`storage_secret`) and **L3** (rate limiting) matter once server mode is the focus.

### Validate + harden the container path
- Actually run `docker compose up --build` end to end (never done yet): confirm
  the Dockerfile builds, real CLIP loads, NiceGUI serves, bind mounts work,
  EXIF writeback through a mount works, `send2trash` → managed-trash path fires
  inside a Linux container.
- Add a compose `healthcheck` (the `curl` is already in the image for this).
- Deps-only pre-layer in the Dockerfile so editing code doesn't bust the
  ~150 MB torch wheel layer on rebuild.
- Build from `uv.lock` like the desktop apps: Docker still runs
  `uv pip install --torch-backend=cpu .` because the lock's Linux torch is the CUDA build.
  Needs a CPU torch source in the lock (or a separate Linux lock).

### Headless server framing
- Document the intended shape: indexer + web UI on an always-on box (NAS /
  home server) chewing through the library 24/7; browse from a laptop; a
  second machine opens the same sync folder and runs **read-only** until the
  lock frees (already built — just needs to be the documented use case).
- `docker compose run --rm indexer --once` / continuous indexer-only mode is
  already there (`profiles: ["tools"]`); make it first-class.

### File-manager helper agent (Docker-only reveal)
- `tools/sortandpost_helper.py` exists and works. Ship the
  `launchd` .plist (macOS) and a `.bat` + Task Scheduler note (Windows) so it
  starts at login; a `/settings` panel showing helper status + a copy-paste
  install command.
- Native runs don't need this at all (reveal works in-process).

### Bind-mount performance notes
- Document that scanning a large library through a macOS/Windows bind mount is
  slow (virtiofs / gRPC-FUSE); recommend the native runtime for the initial
  index and Docker for steady-state on Linux / NAS.

## 10. Missing photos — drop the tile, build out the filter  _(P9)_ ✅
Why: the Settings → Overview "missing" tile is a bare count with nothing to act on, and on a
second computer it mostly counts photos that only exist on the other one (see `Questions.md`).
- Remove the "missing" tile from Settings → Overview. The status bar shows its "N missing"
  part only while a library folder is offline (unmounted / unplugged).
- Rework the library's ⋯ "Show missing files" filter so it shows **only** the missing photos
  (today it adds them to the normal grid).
- Give each missing photo a reason: **"folder offline"** (its last-known path is under a
  library folder that isn't there right now) vs **"file gone"** (the folder is there, the file
  isn't). Show it on the tile and on the photo page next to the last-known path(s).
- Count missing **per computer**: a photo is only missing here if it had a copy under one of
  this computer's library folders. Another device's photos don't count.
- Check first, with a two-machine test: a full scan's presence sweep judges *every*
  `photo_paths` row, including the other computer's paths, and `missing_since` lives in the
  shared DB. So machine B may mark A-only photos missing, publish that, and A shows them
  missing until its own next scan. Fix the sweep to only judge paths under this machine's roots.
- Not in scope: a "Remove N missing photos from the library" action (explicit, confirmed,
  `unindex` changes row, files untouched) — note for V4 if still wanted.

## 11. "Rebuild AI index" button  _(P10)_ ✅
Why: the only way to re-embed today is `python -m sortandpost.indexer --reembed`, which the
packaged Mac/Windows app can't run (no `python`, and the executable doesn't pass `--reembed`
through). Settings shows that command as a hint (found while reviewing the copy CSV, row 103).
- Add a **Rebuild AI index** button to Settings → Indexing & AI → "AI search & tagging"
  (shown while CLIP is on; needs the write lock). A confirm dialog says what it does:
  every photo's AI fingerprint is recomputed, search and "more like this" are incomplete
  until it finishes, it can take hours on a big library, and approved / rejected suggestions
  are kept (only pending ones are regenerated).
- Run it through the indexer's own background thread (a request flag the service loop picks
  up), never beside it: a re-embed deletes the matrix, and a normal CLIP pass running at the
  same time would write into it. Progress shows in the status bar's "embedding" stage; Pause
  and Quit stop it between batches, and the next pass carries on.
- When the indexer hits a model mismatch (it currently only logs "CLIP pass needs --reembed"),
  show a banner on `/` + Settings with the same button.
- **Remove** the "Rebuild the CLIP matrix from the CLI: python -m sortandpost.indexer --reembed"
  label, and reword the `--reembed` hints in `clip/store.py` / `indexer/service.py` error
  messages to point at the button (the CLI flag stays for Docker / source runs).
