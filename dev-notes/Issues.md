- [x] The app froze while changing the group-by (2026-09-27)
  - Cause: not group-by, and not the server (it stayed responsive). Flat mode did it too; group-by just got there faster. Likely triggered on waking the Mac (reconnect -> reload -> restore).
  - Fix: `ui.run(tailwind=False)` + a prebuilt `src/sortandpost/resources/tailwind.css` (Tailwind 4.1.13, same as NiceGUI bundles) from `tools/tailwind/build.sh`. At ~320 tiles: 21 stalls >100ms (worst 450ms) -> 0. Computed styles identical on all 203 class strings shared by prod and dev across every page. Test: `tests/test_tailwind_css.py`.
  - Status: shipped in v1.1.0.
  - Possible follow-up: window/cap the grid's DOM and chunk the scroll-restore render, so a reload after a very deep scroll stays cheap.

## Stress test 2026-10-15 (pre-release; scratch instance, hostile library, two simulated machines)

Fix in this order, one per session. Each entry has the repro and the code location.

- [x] **S1. A conflict copy that fails to merge leaves a "zombie writer" -> two machines editing at once.** Repro: put a conflict copy in `sync/` whose `changes` has an op this version doesn't know (`op='frobnicate'`; also try a rate with `new_value='abc'` / `'99'`, a row for an unknown `pixel_hash`, and a "conflict copy" that is plain text). `sync/merge.py:214` (`_union_changes`) raises `LookupError` (enum). It is raised inside `SyncManager.refresh` (`sync/manager.py:178-183`) and `start` (`:159-163`) *after* `_acquire()`, so `_reconcile_generation` / `_verify_or_restore` / `_start_thread` never run: no heartbeat, no publish, yet the UI says WRITABLE and accepts edits (boot logs "sync layer failed to start; continuing read-only" while the UI says WRITABLE). After `lock_stale_after_sec` the other machine takes the lock -> both WRITABLE (seen). The bad copy is never archived, so this repeats on every boot / promotion. Realistic trigger: mixed app versions (a newer app adds a `ChangeOp`). Fix: merge skips/logs rows it can't apply (unknown op, unparseable value, out-of-range stars) instead of failing; a copy that still can't merge is quarantined (e.g. `snapshots/unmergeable/`) and reported in `/settings`; make `start`/`refresh` exception-safe so a writable mode always has its heartbeat thread (or releases the lock and goes read-only, and the UI agrees).
  - Fixed (2026-10-15): merge skips + counts rows it can't apply, commits per source and quarantines a source that still fails in `sync/snapshots/unmergeable/` (listed in `/settings`); `SyncManager._become_writer` releases the lock and stays read-only (retry in 60 s) if a step after taking the lock fails.
- [x] **S2. One undecodable file aborts every small / scoped scan, forever.** `indexer/scan.py` `_decode_stream._inline` (`:327`) calls `decode_local` with no try/except; only `persist_decoded` is wrapped (`:262-275`). Inline is used for scoped (watchdog) passes and any pass with < `_MIN_FILES_FOR_POOL` (8) files to do. A `PIL.Image.DecompressionBombError` (not a `DecodeError` -- `decode.py` only catches `UnidentifiedImageError/OSError/ValueError`) -> "indexer cycle failed", files after it never indexed, the file gets no `scan_state` row so it is retried every cycle, and the presence sweep + tombstone application never run. Repro: drop a 40000x30000 PNG (tiny, zlib zeros) plus 2 JPEGs into a watched folder. Fix: catch `Exception` around the inline decode the same way the pool path does (`_worker_crash`), and treat `DecompressionBombError` as a `DecodeError` in `load_image`. Also consider: a file that kills a pool worker (`BrokenProcessPool`) is retried inline in the main process -- a crash/OOM there takes the app down.
  - Fixed (2026-10-15): `load_image` turns `DecompressionBombError` into a `DecodeError` (RAW previews too); the inline decode catches any exception per file like the pool path. A worker death no longer retries its in-flight files in the app process: finished ones keep their results, the rest are recorded `decode: worker crashed` (attempts cap applies) and the pass goes on with a fresh pool; later passes decode such a suspect only in a throwaway one-worker pool (`_decode_isolated`), even in a small inline pass. Remaining edge: a pool that breaks before any file returns is still treated as "can't run here" and decodes inline.
- [x] **S3. Failed exiftool writes are reported as success.** `metadata/__init__.py:291` `_commit` checks `"image files updated" in report`, which matches exiftool's failure output `"0 image files updated"` (and `"0 image files unchanged"`). Read-only files, locked / in-use files, read-only NAS shares: the UI says "rated 2★", nothing is written, nothing logged. Repro: `chmod 444` a JPEG, rate it. Fix: parse the count (`(\d+) image files (updated|unchanged)` with N >= 1) and treat "files weren't updated due to errors" as failure; consider telling the user (toast / settings) when file writes fail.
  - Fixed (2026-10-15): `_commit` parses exiftool's summary counts (≥ 1 updated/unchanged, none "weren't updated due to errors"); a read-only / locked file says `Error opening … for writing` without the `Error:` prefix, so it was missed before. `metadata.collect_write_failures` collects one thread's failed writes; UI writes (rate, bulk rate/tag, photo-page tags, /review) go through `app._io_write`, which toasts "Saved in the library, but couldn't write it into …".
