# Issues I have tracked while using sortandpost
- [x] When searching and clicking on a specific image, the arrow controls should page through the filtered images rather than through the main library
- [x] Sometimes when scrolling through photos using arrow keys and rating them using 1-5 it stops being able to scroll -- maybe do a stress test to replicate this behavior
  - Cause (2026-09-27): not load/timing -- stress tests (200 arrow+rate pairs on the grid, 80 on the photo page) never stuck. NiceGUI's `ui.keyboard` drops every key while an input/select/textarea/button has focus; closing a filter dropdown (Stars/Camera/Folder/Subject) or the search box with Esc left focus in its (hidden) `<input>`, so all shortcuts went silently dead until you clicked the page background.
  - Fix: `_KEY_FOCUS_GUARD_JS` in `app.py`, installed after the grid / photo page / `/rate` keyboards -- Esc (on keyup) blurs a focused field; an arrow/digit/letter on a focused button blurs it and goes through (Space/Enter/Tab left to the button). Test: `tests/test_key_focus_guard.py` (skips without Playwright).
  - Status: shipped in v1.1.0 (with the photo-page `<img>` sizing change).
- [x] The app froze while changing the group-by (2026-09-27)
  - Cause: not group-by, and not the server (it stayed responsive). The browser tab ran out of CPU: NiceGUI's in-browser Tailwind compiler rescans every element's classes on each DOM mutation, so each infinite-scroll batch cost more than the last (83% of the tab's CPU; 400-670ms frames by ~300 tiles, up to ~47s stalls by ~800). The frozen tab missed socket.io heartbeats, the websocket dropped, NiceGUI reloaded the page, and scroll-restore re-rendered every loaded tile at once -- a freeze/reload loop. Flat mode did it too; group-by just got there faster. Likely triggered on waking the Mac (reconnect -> reload -> restore).
  - Fix: `ui.run(tailwind=False)` + a prebuilt `src/sortandpost/resources/tailwind.css` (Tailwind 4.1.13, same as NiceGUI bundles) from `tools/tailwind/build.sh`. At ~320 tiles: 21 stalls >100ms (worst 450ms) -> 0. Computed styles identical on all 203 class strings shared by prod and dev across every page. Test: `tests/test_tailwind_css.py`.
  - Status: shipped in v1.1.0.
  - Possible follow-up: window/cap the grid's DOM and chunk the scroll-restore render, so a reload after a very deep scroll stays cheap.
- [x] When scrolling through the library, there is a small gap between the top bar of the page and the top of the header for the group by category. I think it would look better with this gap removed
  - Cause: the sticky section header used Tailwind `top-16` (64px); the app bar is ~60.4px, so photos showed through a ~3.6px strip. On a narrow window the bar wraps to ~102px and the header slid under it.
  - Fix (2026-09-30): `_APPBAR_HEIGHT_JS` publishes the bar's measured height as `--sp-appbar-h` (ResizeObserver); `.sp-section-header` sticks at `top: var(--sp-appbar-h)`. Hands-on tested.
- [x] **The whole app freezes while a macOS Keychain prompt is open** (found 2026-09-30 testing the rebuilt `.app`). `/settings` reads the robopost API key (`keyring` → `SecItemCopyMatching`) on the web event loop; a rebuilt ad-hoc-signed app has a new signature, so macOS asks for Keychain access and every page hangs until the prompt is answered. Affects anyone with a saved robopost key, after every update, until the app is Developer-ID signed. Fix: keychain reads off the event loop + cache the key per process (see PROGRESS.md). Deferred to the next build.
  - Fix (2026-10-05): every keychain call runs off the event loop (`run.io_bound`), and the key is read once per process and cached (`secrets_store.get_robopost_key` / `cached_robopost_key`; save / remove keep the cache current). Settings → Posting shows "Checking the keychain…" until the read finishes; the compose page shows the same while it checks. Test: `tests/test_keychain_off_loop.py` (a keyring that blocks like an open prompt; the page still renders).
- [x] Paging through photos on `/photo/{pixel_hash}` with arrow keys flashes the whole window white on some navigations -- Firefox on Windows and Mac (~1 in 3), Safari on Mac (~1 in 10); seen in dark mode.
  - Cause: the theme CSS (`body{background-color:var(--sp-bg)}`) applies before Vue mounts, but the `body--dark` / `sp-season-*` classes only arrive at mount, so `--sp-bg` is the `:root` light default (`#faf8f4`) for that instant. Firefox / Safari sometimes paint it; Chromium holds the paint.
  - Fixed: `themes.first_paint_css` (in the page `<head>`) also sets `--sp-bg` for the resolved look. Hands-on tested 2026-09-30.
- [x] **The photo page shows no tags** (found 2026-10-02 while testing the security fixes). `/photo/{pixel_hash}` has never had the tag UI CLAUDE.md specifies ("manual tag editor, CLIP suggestion chips (approve/reject)"): checked back to V1 P4 (`79f39a5`). Tags can only be added from the library's bulk toolbar, and suggestions are only reviewable in `/review`. To build: list the photo's tags (manual + CLIP-approved) as removable chips, an add-tag input (`add_manual_tag` / `remove_manual_tag` via `run.io_bound`, disabled in read-only mode), and pending CLIP suggestions with approve/reject. Tag names go through `sortandpost.tag_names` (see Security.md C1).
  - Fix (2026-10-02): a Tags section in the photo page's info column, between the facts and Paths -- applied pills (✕ removes manual tags), dashed "ghost" pills for pending CLIP suggestions with ✓ approve / ✕ dismiss, and an add-tag input. `_photo_tag_state` / `_apply_photo_tag` in `app.py` run off-loop and reuse `add_manual_tag` / `remove_manual_tag` / `approve` / `reject`, so every change writes a `changes` row and re-embeds the keywords into the file. Controls hidden in read-only mode. Hands-on tested.
  - Follow-up (2026-10-05): ✕ on approved CLIP tags too (`clip.tagging.unapprove`: drops the tag, rejects the suggestion so it isn't re-suggested, `tag_remove` + `clip_reject` change rows), and in a stack tags now live on the top photo only (the JPEG when the top is a RAW): adding / approving tags goes there, removing clears every member, and "Make this the top photo" moves the tags to the new top. Tagging never writes a hidden member's file, so it can't change the top.
- [x] Issue with arrow navigation when rating photos -- If I am going through photos and rate one of them Photo A, then go to the next photo Photo B and rate it, then go back to Photo A and change its rating, the arrow keys stop working and I have to go back to the library and reopen the photo
  - Cause (2026-10-03): the stack issue below. Rating a stack wrote every member's file, so the last member written had the newest mtime and became the stack's new top photo after the rescan. The photo page finds its prev/next in a cached snapshot of the grid order, which still held the old top hash, so `neighbors()` returned nothing and both arrows went dead.
  - Fix: the stack fix below stops our own writes from flipping the top. Also, the photo page now looks itself up as its top photo or any stack member (`library_view.locate`), and re-resolves the view once if the cached order has none of them. Tests: `tests/test_stack_file_writes.py`, `test_locate_finds_a_stack_whose_top_photo_changed`.
- [x] When rating or tagging images, it rates both images in the stack. I only want the data written to the image on the top of the stack, because it changes the modified date of the original
  - Fix (2026-10-03): ratings / tags still go to every stack member in the DB (grid + filters stay consistent), but only the stack's embed target is written: its newest member that can carry metadata (`stacks.embed_target`; for RAW+JPEG the JPEG). This covers the photo page, bulk rate/tag, `/rate`, and `/review` approvals (`app._file_exif`). The indexer's reconcile no longer writes a DB rating back into a non-target member's file (`reconcile_metadata(write_back=False)`, using a folder-scoped `build_stacks`). Hands-on tested on dev; prod check pending.
  - Follow-up (2026-10-03): a **"Make this the top photo"** button beside a stack's filmstrip on the photo page (`app._apply_make_top`). It rewrites that photo's own rating and keywords into its file (`ExiftoolClient.restamp`: always rewrites the file, writing unrated as an explicit `XMP:Rating=0`), so its mtime becomes the stack's newest and it becomes the top photo and embed target. It never writes a RAW. Use it to fix stacks whose original got bumped to the top by the old fan-out writes; the stale ratings already embedded in those originals stay there. Hands-on tested.
- [ ] When exiting app on Mac OS, it does not appear to move things to trash when I tell it to move things to trash
  - Cause (2026-10-08): same root cause as the prod crash below. The managed trash lives in `local/trash/`, which on prod is inside the Synology Drive folder (a macOS File Provider volume). `send2trash` fails there on every batch ("The volume doesn't have a trash" / "You don't have permission"); the tray logs `{'moved': 0, 'failed': 5}` on each Quit. Moving `local/` out of the synced folder (below) should fix it; also surface the failure in the Quit dialog instead of only the log.

- [x] **Prod crashed and wouldn't boot: `disk I/O error` on the working DB** (2026-10-08 15:08)
  - Cause: prod is a legacy **single-folder** install (`~/.sortandpost/app_data_path.json` = `{"app_data": ".../SynologyDrive-<user>/Film and digital/sortandpost"}`), so `local/` -- the working DB, its rollback journal, `trash/`, `models/`, logs -- sits inside Synology Drive's on-demand (File Provider) folder. Mid-transaction Synology evicted `local/sortandpost.db-journal` (`ls -lO` showed `compressed,dataless`, 0 blocks) before it had uploaded it, so it could never be fetched back (`Stale NFS file handle`). SQLite must read a hot journal to roll back on every open, so every query failed, and every boot died in `db/engine.py` `_set_pragmas` (server exit 1).
  - Why boot didn't self-heal: `app.build_ui` calls `init_db(engine)` (`app.py:887`) **before** `manager.start()` (`app.py:895`), so the startup `quick_check` -> restore-snapshot path never ran.
  - Fixed by hand: the working DB alone passed `integrity_check` and held the 6 ratings made at 15:08 (the hot journal belonged to an indexer re-read, nothing user-authored). Backed up both DBs to `~/Library/Application Support/sortandpost/recovery-20261008/`, renamed the journal to `local/sortandpost.db-journal.dataless-20261008` (delete once prod is confirmed healthy). Prod booted writable and published generation 159.
  - **Permanent fix shipped (2026-10-08, branch `fix/local-out-of-sync-folder`; hands-on tested on a simulated Synology install):** steps 1, 2, 4, 5 and 6 below are built -- `sortandpost.cloud_folders` (detect a sync tool's folder), `sortandpost.relocate` (automatic move of a single-folder `local/` out of it at startup; a real `APP_DATA` env var only warns), `sortandpost.sync.recovery` (boot recovery before any open: set aside, rebuild from published / newest snapshot, merge salvaged unpublished edits), daily snapshots (`sync.snapshot_every_hours: 24`) + Settings "Back up now" / last backup, `/` banners. Tests: `test_sync_recovery.py`, `test_relocate.py`, `test_sync_manager.py`. Still open: check the Windows machine after it gets the new build (the move is automatic now).
  - **Permanent fix -- plan:**
    1. **Never keep `local/` inside a synced folder.** Migrate prod to the split layout: pointer becomes `{"sync_dir": ".../sortandpost/sync"}`; copy `device.json` (keeps the same `device_id`, so the lock and `sync/devices/<host>-<id8>/` stay this machine's), `onboarding.json`, `publish_state.json`, `sortandpost.db`, `trash/` (+ manifests), `ui_prefs.json`, `logs/` into `~/Library/Application Support/sortandpost/libraries/<name>-<hash8>/`; move `models/` to the shared `<local root>/models`. Do it with the app stopped; leave the old `local/` in place until the new one boots, then remove it from the Synology folder.
       - **Before migrating, make sure nothing is left unpublished in the old `local/`:** quit the app cleanly (the final publish runs on shutdown), check that `sync/sortandpost.db`'s `db_generation` equals the working DB's, compare their `changes` row counts / `max(ts)`, and check that Synology has finished uploading `sync/sortandpost.db` (not `dataless`, no pending sync). If the working DB is ahead, boot once more and quit cleanly before copying. The built-in migration (step 2) should run the same check and refuse to move until the published copy matches.
       - **Done for the Mac (2026-10-08):** published copy == working DB (generation 161, byte-identical, lock released). Copied to `~/Library/Application Support/sortandpost/libraries/sync-d9c9c4be/` (same `device_id`), CLIP weights to `~/Library/Application Support/sortandpost/models/`, pointer switched to `{"sync_dir": ".../sortandpost/sync"}` (old pointer saved in `recovery-20261008/`). Booted writable, no wizard, indexer clean, published generation 162. Old `local/` moved to `~/Library/Application Support/sortandpost/recovery-20261008/old-local/` and removed from Synology. **Still to check: the Windows machine** (`desktop-cdmgf7f`, `C:\Users\thefi\SynologyDrive\...`) -- if its `local/` is also inside SynologyDrive, migrate it the same way.
    2. **Make it a built-in migration for other users**, not a manual step: at startup, if the resolved layout is single-folder (legacy pointer, `.env`, or a non-Docker `APP_DATA`) and `local/` is inside a cloud-sync location (`~/Library/CloudStorage/*`, iCloud `Mobile Documents`, OneDrive / Dropbox / Google Drive / Synology roots on Windows), offer "Move this computer's working files out of the synced folder" (Save & restart, same flow as Settings -> Shared library folder) and show a warning banner until done. Docker keeps `APP_DATA` single-folder (its `/data` mount isn't a File Provider), but the warning should still fire if the host path is a cloud folder.
    3. **What stays synced** (unchanged by the split -- this is how settings and backups keep travelling between computers and across any provider: Synology Drive, OneDrive, Dropbox, Google Drive, iCloud): `sync/config.yaml` (app settings), `sync/profile.json`, `sync/tags.yaml`, `sync/devices/*/library.json` + `achievements.json`, `sync/collections.json`, `sync/posts/`, the published `sync/sortandpost.db`, `sync/snapshots/*.db.zst`, thumbnails and embeddings. Only machine-specific state (working DB, publish state, trash, CLIP weights, logs, `ui_prefs.json` theme) stays local -- if per-machine look should follow you too, move it to a synced per-device file like `library.json`.
    4. **Better DB backups in the synced folder.** Snapshots only happen every 20 publishes, so prod had just two (Sep 27, Oct 3) and only one snapshot covered the last week. Add a time-based snapshot (e.g. at least daily while dirty, plus one at clean shutdown), keep `snapshot_keep` dailies, and show "last backup" in Settings -> Sync & storage with a "Back up now" button. Snapshots are compressed copies written with tmp + `os.replace`, so they're safe in any provider.
    5. **Boot recovery.** Open the working DB through the sync manager's checks before `init_db`: on a connect/`quick_check` failure (incl. `disk I/O error`, a hot journal that can't be read, `dataless` files), move the broken working DB + journal aside to `local/broken-<ts>/`, then take the newer of the published `sync/sortandpost.db` (if it passes `quick_check`) or the newest snapshot, and run a reconcile scan. Show what was recovered on `/settings`. Test: a fake hot journal that raises EIO on read.
    6. **Hydrate before use.** If `sync/sortandpost.db` or a snapshot is itself dataless at startup, do a bounded read to force the download (like `indexer.hydrate`) before copying it, and report clearly if the provider can't supply it.
