# sortandpost — v2 roadmap

Everything deliberately deferred past the first production release. v1 is
"organize photos locally, index/ratings/tags/embeddings travel in a sync
folder, run it natively." v2 is the list below.

_Created 2026-09-10. Order within a section is rough priority, not a schedule._

---

## Features

### 1. Social media post composer (robopost.app)
The last unchecked `Features.md` item, and the app's namesake half.

- Group photos into a post with caption text; reorder; per-image alt text.
- Push to the **robopost.app API** — upload media, create a post, schedule for a
  future time.
- API key lives in `.env` (per-machine, never synced), same pattern as
  `PHOTO_LIBRARY` / `APP_DATA`.
- Build on **Collections** — a collection is already an ordered, de-duplicated
  photo group with a notes field. A "post" is a collection + schedule metadata +
  a publish log.
- New page `/compose` (or an action on a collection). Draft state stored like
  collections (`sync/posts.json` or extend `collections.json`).
- Guardrails: never auto-post; explicit "Schedule" button behind a confirm;
  show what will be uploaded and where.

### 2. `/search` filter UI completion
The `PhotoFilter` model and `allowed_hashes` plumbing already support these —
only the widgets are missing.

- Date-range picker (taken_at from/to).
- Tag AND / OR selector (multi-tag).
- Currently wired: stars ≥ N, camera, has-GPS, duplicates, missing.

### 3. Per-photo `/review` controls + facet grouping
Today `/review` is per-tag bulk approve/reject only.

- Per-prediction approve/reject on individual photos.
- Group pending predictions by facet (scene / subject / lighting / …), not just
  a flat tag list.

### 4. Desktop app feel
- NiceGUI `native=True` (pywebview) — a real window instead of a localhost
  browser tab. Small change; pairs with the native-first runtime.
- Optional: a menu-bar / tray item to start/stop the indexer.

### 5. Packaged distribution (no terminal, no Python)
- PyInstaller or Briefcase single-file bundle with a **vendored `exiftool`**
  binary and the rawpy / pillow-heif native libs.
- CLIP weights downloaded on first run (needs network once) rather than bundled
  (~600 MB).
- Produces a double-clickable `.app` / `.exe` / AppImage.

## Deployment — Docker / NAS / server mode

v1 ships Docker as-is but the docs will frame **native as the default**. v2
turns the container into a proper always-on server story.

### 6. Validate + harden the container path
- Actually run `docker compose up --build` end to end (never done yet): confirm
  the Dockerfile builds, real CLIP loads, NiceGUI serves, bind mounts work,
  EXIF writeback through a mount works, `send2trash` → managed-trash path fires
  inside a Linux container.
- Add a compose `healthcheck` (the `curl` is already in the image for this).
- Deps-only pre-layer in the Dockerfile so editing code doesn't bust the
  ~150 MB torch wheel layer on rebuild.

### 7. Headless server framing
- Document the intended shape: indexer + web UI on an always-on box (NAS /
  home server) chewing through the library 24/7; browse from a laptop; a
  second machine opens the same sync folder and runs **read-only** until the
  lock frees (already built — just needs to be the documented use case).
- `docker compose run --rm indexer --once` / continuous indexer-only mode is
  already there (`profiles: ["tools"]`); make it first-class.

### 8. File-manager helper agent (Docker-only reveal)
- `tools/sortandpost_helper.py` exists and works. v2: ship the
  `launchd` .plist (macOS) and a `.bat` + Task Scheduler note (Windows) so it
  starts at login; a `/settings` panel showing helper status + a copy-paste
  install command.
- Native runs don't need this at all (reveal works in-process).

### 9. Bind-mount performance notes
- Document that scanning a large library through a macOS/Windows bind mount is
  slow (virtiofs / gRPC-FUSE); recommend the native runtime for the initial
  index and Docker for steady-state on Linux / NAS.

## Polish

### 10. Design pass — round 2
First cut shipped 2026-09-10. Detailed feedback coming. Likely targets:

- Card-definition strength; how far the serif display face leans.
- Header density; accent-color weight.
- `ui.input` / `q-field` styling consistency.
- `/search`, `/review`, `/photo` layout fit; photo-page composition.
- Dark-mode treatment of the white `ui.toggle` buttons.

### 11. Bulk-delete follow-ups
The delete action itself is done (move-to-trash + tombstones + cross-machine
lazy purge).

- In-app **"undo last delete"** using the managed
  `local/trash/<ts>/manifest.json`.
- A `/settings` view of the local trash folder (list, "reveal", "put back").
- A live two-container test of the cross-machine lazy-trash path (unit-tested
  only so far).

### 12. Group-by infinite-scroll race
Collapsing a large section gives it ~zero height, so infinite scroll can race
to the end and a later Expand-all redraws many tiles at once. Fine at ≤25k
photos. Fix if it bites — e.g. pause auto-append after N all-collapsed batches.

### 13. `/review` exiftool reuse
Each bulk approve/reject spawns its own `exiftool -stay_open` process. Share
one serialized client across a review session.

## Robustness & scale

### 14. In-app indexer lock re-check
A web session that starts in read-only mode never promotes itself to indexing
until the process restarts — the in-app indexer thread reads `manager.mode`
without calling `manager.refresh()`. The standalone `python -m
sortandpost.indexer` entrypoint does re-check. Harmless for single-machine
use; matters once two machines share a sync folder.

### 15. Targeted subtree rescan on FS events
A `watchdog` event currently schedules a debounced **full** `scan_once`.
Correct, just not minimal — rescan only the affected subtree.

### 16. RAW + HEIC end-to-end audit
Decode real `.CR2` / `.NEF` / `.HEIC` via embedded preview and **verify
constraint #2**: RAW files are never written to or beside (check mtimes + logs
before/after a rating write). Partly exercised (a full native index incl.
`.CR2` + `.HEIC` ran clean) but the no-write property isn't formally audited.

### 17. ANN index for > ~25k photos
Semantic search is brute-force NumPy cosine over a memmap matrix — the design
target is ≤25k photos. Past that, add an on-disk ANN index (hnswlib /
sqlite-vec) **behind the existing search interface** — do not change the
interface.

### 18. Near-duplicate detection polish
dHash is weak on near-flat images (a solid-color frame hashes to all-zero, so
solid frames cluster). Real photos have gradients. Revisit only if it produces
bad duplicate groups in practice.

### 19. Windows pass
rawpy / pillow-heif / send2trash / `explorer /select,` reveal / Windows-compat
rating tags (`EXIF:Rating`, `XMP-microsoft:RatingPercent`) all have code
paths; none run on real Windows yet.
